### 2.1 Why Route Groups

Route groups (`(name)`) let us share layouts without affecting URL paths.

- `(auth)` — login, pending — no app chrome
- `(owner)` — owner/admin app — sidebar + topbar
- `(crew)` — crew mobile — bottom nav
- `(onboarding)` — wizard — minimal chrome

URL: `/dashboard`, `/crew/event/PRJ-123`, `/onboarding/step-3` — clean URLs without route group names.

### 2.2 Layouts

Each route group has its own `layout.tsx`. Auth checks happen in middleware + per-layout (defense in depth).

### 3.1 Component Conventions

- **Server Components by default.** Add `'use client'` only when needed (interactivity, hooks, browser APIs).
- **One component per file** for top-level. Sub-components can co-locate if tightly coupled and not reused.
- **Co-located schemas:** Form components have `schema.ts` next to them.
- **Index files (`index.ts`)** only for folders that export multiple things meant for external consumption.

### 3.2 When to Promote to `custom/`

Move a component from `modules/x/` to `custom/` when it's used in 2+ modules and feels generic enough.

### 4.1 Key Patterns

**Server Actions = `'use server'` directive at top of file:**

```ts
// lib/actions/events.ts
'use server';

import { z } from 'zod';
import { CreateEventSchema } from '@/lib/validations/events';
import { requireAuth } from '@/lib/auth/require-auth';

export async function createEvent(input: unknown): Promise<ActionResult<Event>> {
  const user = await requireAuth(['owner', 'super_admin']);
  
  const parsed = CreateEventSchema.safeParse(input);
  if (!parsed.success) {
    return { success: false, error: { code: 'VALIDATION_ERROR', message: parsed.error.message } };
  }
  
  // ... business logic
}
```

**Calculations are pure functions:**

```ts
// lib/calculations/settlement.ts
export function calculateNetProfit(input: SettlementInput): SettlementResult {
  // No DB access, no side effects, just math
  return {
    netProfit: input.revenueNet - input.totalBiaya,
    isLoss: input.revenueNet - input.totalBiaya <= 0,
    // ...
  };
}
```

This separation makes business logic testable and reusable.

## 10. Naming Conventions

### 10.1 Files

| Type | Convention | Example |
|------|-----------|---------|
| Components | kebab-case | `event-card.tsx`, `data-table.tsx` |
| Pages (App Router) | always `page.tsx`, `layout.tsx`, etc. | (Next.js convention) |
| Hooks | kebab-case with `use-` prefix | `use-debounce.ts` |
| Utilities | kebab-case | `format.ts`, `id-generator.ts` |
| Types | kebab-case | `database.ts`, `domain.ts` |
| Server Actions | kebab-case (matches module) | `events.ts`, `payments.ts` |
| Validations | kebab-case (matches module) | `events.ts` |
| SQL Migrations | timestamp + snake_case description | `20260101000000_initial_schema.sql` |

### 10.2 Variables & Functions

| Type | Convention | Example |
|------|-----------|---------|
| Variables | camelCase | `eventId`, `crewAssignments` |
| Constants | UPPER_SNAKE_CASE | `DEFAULT_DP_AMOUNT`, `OWNER_POOL_PER_PERSON` |
| Functions | camelCase | `calculateNetProfit`, `formatIDR` |
| Server Actions | verbNoun camelCase | `createEvent`, `closeSettlement` |
| React Components | PascalCase | `EventCard`, `KPICard` |
| Types/Interfaces | PascalCase | `Event`, `CreateEventInput` |
| Enums (TS) | PascalCase | `EventStatus`, `ChannelType` |
| Enum values (TS) | snake_case (matches DB) | `'awaiting_settlement'`, `'super_admin'` |
| Database tables | snake_case | `events`, `crew_assignments` |
| Database columns | snake_case | `event_date`, `created_at` |
| Database enums | snake_case values | `'photobooth_classic'`, `'super_admin'` |

### 10.3 IDs & References

- `id` — primary key UUID
- `xxx_id` — foreign key (e.g., `event_id`, `user_id`)
- `ref_id` — human-readable reference (e.g., `PRJ-20260501-1234`, `PAY-...`)
- `code` — short identifier for system entities (e.g., `equipment` for sinking fund)

## 11. Import Patterns

### 11.1 Path Aliases

`tsconfig.json`:

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

**Always use `@/` aliases**, never relative `../../..`:

✅ Good: `import { Button } from '@/components/ui/button';`
❌ Bad: `import { Button } from '../../../components/ui/button';`

### 11.2 Import Order (enforced by Biome)

1. External packages (`react`, `next`, `lucide-react`)
2. Internal aliases (`@/lib/...`, `@/components/...`)
3. Relative imports (only `./` when sibling)
4. Type-only imports (with `type` keyword)
5. CSS imports

```ts
import { useState } from 'react';
import { useRouter } from 'next/navigation';
import { Button } from '@/components/ui/button';
import { createEvent } from '@/lib/actions/events';
import { formatIDR } from '@/lib/utils/format';
import { EventCard } from './event-card';
import type { Event } from '@/lib/types/domain';
import './styles.css';
```

### 11.3 Re-exports

Use `index.ts` only when:
- Folder represents a logical unit (e.g., `components/custom/data-table/`)
- External consumers benefit from grouped imports

**Avoid** barrel exports for everything (slows down builds, complicates tree-shaking).
